# FPGA 选题与范围规划

## 用途与适用场景

在选题、核心价值不清、功能不断扩张或工期明显变化时使用。根据已授权的目标推进；用户已有题目时，先评估如何完善该题目，未经明确讨论不替换成另一个项目。

## 输入与前置条件

取得实际使用者及其任务、现有原型与原始证据、赛题/验收要求、可用板卡与测试源、人员和时间约束。分别标注已知、推断和待核实项。旧计划与新消息冲突时，记录后续明确决定如何调整旧约束；不把过期的待办或 PASS 当作当前状态。

截止时间、组别和必交文件以当次有效来源核对；存在冲突时注明来源和不确定性，安排保守的内部节点。不要把本项目曾用过的日期或评分口径写成通用规定。

## 执行步骤

1. **写清要改变的结果。** 用“谁在什么场景遇到什么困难，完成后能据什么作出判断”描述价值。例如：设备操作者能看见异常原因、发生时刻和前后数据，并能回读复核。区分数据监视、异常检出和故障根因诊断，选择当前证据能够支持的目标。
2. **盘点已有能力与缺口。** 对采集、解析、判断、保存、查看、恢复逐项标注未实现、离板通过、实板通过或用户确认，绑定版本。界面截图、测试源输出和真实设备记录各有作用，不能相互替代。
3. **比较有实质差异的方向。** 对必要的候选方案说明价值增量、FPGA 承担的任务、复用范围、前置依赖、验证成本和退路。不为凑数量列方案，不用没有依据的加权分数制造精确排名。新增接口应解决明确接入障碍；“再多一种总线”本身不足以证明价值。
4. **选一个可证明的最小闭环。** 对监测项目，可用正常输入、可控异常、前后数据留存及独立回放建立主线；若主张配置复用，还需用不同格式证明切换边界。每条核心宣传语都要有对应实验或明确标为待验证假设。
5. **把范围分成此次必做、可延后和触发扩展的条件。** 一项依赖缺失时继续软件、向量、仿真和接入准备；实线项目保持待验，不偷偷改成仿真通过。合成源用于可控验证，真实设备用于实际场景，两者身份要保留。
6. **倒排关键路径并留提交缓冲。** 从可用实验窗口、数据回取、复核和交接反推次序，写清谁做、需要什么、完成凭据在哪里。把可重复的复杂电脑操作做成脚本；报告、打包和其他材料遵从用户当前安排，不因规划而自动开工。
7. **遇到新证据时更新决定。** 新硬件可用、用户目标改变、原假设被否定或预计无法按时验证时，说明调整理由、被替代的假设和影响范围。已有可用基线及其历史证据继续保留。

## 失败条件与处理

没有可描述的使用者任务、无法观察目标效果、关键资源完全无着落或计划只剩功能堆积时，缩小待验证主张并先做低成本验证。创新性、得分和普适性没有证据时标为假设；不承诺获奖或跨设备即插即用。只有确实影响路线的缺失信息才向用户追问，同时推进不依赖答案的工作。

## 输出与验收

输出简明决策记录：目标用户与问题、候选及取舍理由、本次范围、关键假设、验证清单、依赖/负责人/内部节点、失败后的退路。接手者应能回答“为什么做这个、接下来先做什么、凭什么算完成、什么情况要改计划”。

若用户已要求实施，继续完成已授权且可推进的准备工作，不能止于一张路线表。规划通过只表示路线可执行；产品价值仍需真实使用和实验验证。

## 来源与已验证效果

本项目从专用小车遥测走向 JSON 配置复用，用真实小车二进制和 EGo1 合成文本验证同一 PYNQ 固件；板卡不在身边时先做离板准备。具体用户判断、工程证据与限制见 [project-case.md](references/project-case.md)。这些是项目内已经发生的结果，不证明本技能已在另一题目提高选题成功率。

## 迁移边界与关联资料

判断方法适用于相近 FPGA 项目，具体设备、电平、速率、官方要求和资源需重新核对。案例中的选型与当前项目的授权不自动适用于迁移项目；保留目标用户自己定义的成功标准。
