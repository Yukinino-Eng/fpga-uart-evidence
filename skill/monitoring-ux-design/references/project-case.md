# 案例：让使用者读懂连续故障记录

本文是有出处的协作与工程摘要。用户原话来自本次会话，处理部分不冒充模型逐字回答；来源路径的摘要见整包 source-index.json。

## 用户指出的任务障碍

用户先说“我怎么有点看不懂这个取证界面”“你这几个窗口都长一样是啥意思”，随后提出：

> 窗口多没问题，我们就要记录不同时间的故障，不能只记录一次就必须人工恢复，但记录时清楚的加上记录故障和触发时间，提高可读性，不能让用户去适应我们带来的繁琐

此前还要求协议选择、数据显示更平滑、字段按设备变化、实时状态和多个异常状态保存。

这些反馈指向事件身份、时间和工作流程，不能只通过减少窗口或调整配色解决。

## 采用的设计与关键区分

- 协议配置带出友好字段名、单位、默认曲线和有效性；显示元数据不改变解码和检测。
- 每次事件显示故障、触发时间、编号/第几次、触发依据和保存状态；相似窗口解释同帧共用证据，用户仍能辨认规则和时刻。
- 条件恢复后自动记录下一次事件；持续同一异常不随刷新重复建窗。前窗不足、后窗收集中、保存失败与完整保存分开显示。
- 同一帧的8条规则保留8个事件；约6秒和14秒的两批结果不以“图长得一样”为理由删掉。启动等待提示与设备字段故障分类显示，原始事件仍保留。
- 曲线平滑仅用于呈现，保留原始点和取值；缺失/无效/断流不补0。不把相对硬件时间标成已校准UTC。
- 显示条数、总窗口量和待保存队列各有限额，达到限制需明确提示。页面看到多少条不能直接代表总共保存多少条。

## 实际环境纠正了哪些判断

`docs/uart-monitor/notebook-live-check.md` 记录旧版 ipywidgets.Output 中嵌套显示未出现在真实 Notebook 页面，随后改用明确的子组件结构。纯导出 HTML 能显示不足以证明实际操作入口也正常。

页面曾把已解析帧的时间差直接当超时，联合采集中出现6个错误标签，而硬件超时事件为0。修正为采用检测引擎活动状态或晚于最新有效帧的实际事件后，另做60.050秒静态复测；3006帧完整，54个浏览器观察样本没有错误超时标签。真实超时和恢复显示也另行检查。修复没有修改故障阈值或固件。

## 已有证据支持到什么程度

`docs/uart-monitor/visualization.md` 保留实际小车两次手动倾角的工程说明：两次触发相隔约21.24秒，各自完整保存前后5秒，无需人工重新布防，4399帧独立回放一致。该例电机停止，阈值是演示规则。

最新二进制八路和重启后 Notebook 记录见 `build/uart_latest_binary_acceptance_20261101_01/completion.json` 与 `build/uart_power_recovery_20261101_01/completion.json`；联合采集及浏览器结果见 `build/uart_live_run_20261101/completion.json`。这些支持已测流程可用及数据一致，不支持无限事件保存或所有浏览器负载保证。

## 可迁移的走查任务

| 交给使用者的任务 | 看什么表现 | 不足时怎样定位 |
| --- | --- | --- |
| 说出现在是否在接收、页面是否新鲜 | 能找到状态及依据，不把页面延迟说成设备断流 | 检查状态来源与显示更新时间 |
| 找到某一次故障及触发原因 | 能从列表读出故障、时刻、编号、触发条件 | 调整事件信息层次与时间表达 |
| 恢复后再发生一次同类异常 | 能自动找到第二次独立记录 | 检查触发/恢复状态机和窗口队列 |
| 判断一个窗口是否保存完整 | 能辨别收集中、截短、失败和完整 | 检查保存状态、容量提示和重试动作 |
| 切换设备后查看正确字段 | 名称、单位、有效性与协议一致 | 检查配置映射和切换前置条件 |

这张表是本轮新编的迁移走查方法，不是已经做过的外部用户研究。没有新的盲测、任务耗时对照或陌生队伍验证；本轮没有改生产页面。
