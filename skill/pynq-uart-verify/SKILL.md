# PYNQ UART 采集与取证核验

## 用途与适用场景

用于 UART 采集排错、规则验证、多事件取证和保存恢复。先确定本次要检查线路、规则、保存、板卡恢复还是历史记录；离板任务只读记录，不自动连接板卡。

## 输入与前置条件

需要来源类型、协议/规则配置、固件/软件摘要、原始字节、对应硬件时间、事件台账及采集状态。区分真实设备、合成发送器、RTL 仿真与离线构造，分别记录构建、实板、回放和界面检查。

## 执行步骤

1. 核对身份及通信设置，再看原始字节、时间索引、FIFO、停止位和事件通路错误。先判断采集质量，再归因设备；采集失败不能抹除已有的有效设备告警，证据不足时保留 UNKNOWN。
2. 连续输入下的启停错误按 [workflows.md](references/workflows.md) W2 排查；改变采集开关不应在字符中途无条件复位解码器。真实非法停止位仍要检出。
3. 从相同原始流与硬件时间重新解析，比较字段、有效性、事件身份/时刻及窗口文件。丢失输入时保留无法完整比较的状态，不补造数据。
4. 分开检查异常检出和文件保存。多次异常分别编号并标注故障、触发时刻及窗口完整性；同一持续异常不按页面刷新重复触发，恢复后再异常建立新事件。保存失败保留待处理请求与重试记录。
5. 输出采集、协议、设备、保存四类状态、版本依据和未测项。无校验或无序号时标“不具备判断条件”，不能写成零错误通过。

## 失败条件与处理

输入丢失、时间轴重启、解析无效、事件队列满、保存失败与窗口不足分别记录。离线回放通过不等于新实板通过。硬件访问先满足已知身份、独占锁和空闲条件；未知设计不猜测 MMIO 地址，不绕过保护。

## 输出与验收

`scripts/audit_record.py` 核对 URX2 字节/逐字节64位时间、台账、窗口摘要和预声明期望；显式传入可信 `--project-root` 才执行该工程的软件回放，不创建硬件 Transport。该参数内的 Python 源码会被执行，不能把它当作纯数据。

`scripts/check_project.py` 运行随包八例，期望在 examples/；`scripts/self_test.py` 检查15项正负向行为；`scripts/check_snapshot.py` 严格核验目录文件集合、大小和摘要。工具输出放在输入目录之外，不覆盖已有输出。命令见根 README。

## 来源与已验证效果

来源与用户原话见 [collaboration-cases.md](references/collaboration-cases.md)，细节见 [workflows.md](references/workflows.md)：连续输入修复经过160组相位和37轮F103历史实测；八路规则两批共16个完整设备窗口；故意停读产生834字节丢失并保留设备 UNKNOWN；保存阻塞后重试成功。上述均为已有工程证据，本轮新增的是技能离板核验，见 [validation.md](references/validation.md) 与 [project-evidence.json](references/project-evidence.json)。

## 迁移边界与关联资料

本案例单通道3.3V UART、8N1，一次只接一个 TX；断电前移除外部 TX。引脚、基址、时钟和业务阈值需重新配置；小车沿用用户原按钮流程，监测程序不发控制命令。

八路是并行规则实例，不是八路 UART。硬件时间为运行内相对计数；确认持续时间、PL 处理、PS 读取、页面刷新与落盘延迟分别描述。原始值、换算值和有效性分开，缺失不填0、断流不插值，显示平滑不改证据。正常关机后人工恢复不等于突发断电自动续采。

赛题对应见 [contest-mapping.md](references/contest-mapping.md)。协作案例是有来源的摘要，不能代替完整聊天导出；URX 解析器需适配，不承诺陌生队伍或跨板已经验证。
