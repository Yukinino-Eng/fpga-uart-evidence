# UART 采集与取证操作流程

## W1 已知身份和空闲证明先于硬件访问

**适用场景：** PYNQ 多overlay切换、接手他人工程、重启后显式恢复。DMA设计也可采用该判断顺序，但需其专用状态适配器。

**输入：** 用户授权的操作范围；板卡/镜像版本；目标bit及HWH；当前运行设计的身份机制、时钟、寄存器契约与独占锁。

**步骤：**

1. 保存当前应用未完成的记录。先从已知系统信息核对当前设计，取得工程约定的独占访问权。
2. 对目标bit/HWH建立SHA256配对记录；按契约核对地址、ID、ABI主版本、所需能力位、时钟、FIFO容量。不能只凭文件名判断兼容。
3. 对**已经识别**的运行设计读空闲状态：停止接收、原始FIFO/事件FIFO为空、解析/执行不忙。DMA项目还需相应通道停稳和事件确认。
4. 用户要求加载且前置条件成立时，显式加载目标。回读身份和状态，保持接收停止，再开始新会话。
5. 重启恢复需分别核对Linux启动编号、网络/Notebook、实际overlay、历史文件摘要和新采集。系统默认base.bit不代表监测固件已经恢复。

**失败条件：** 当前设计未知、锁被占用、待读数据或身份不符时保留现场，停止依赖该条件的写操作。授权加载不等于授权刷系统卡、QSPI或更改被测设备。

**输出：** 操作前后身份/空闲收据、目标摘要、是否真正重新加载、历史结果是否一致。

**来源与效果：** C5一次正常关机后的断电恢复，1228个原有文件一致，重新采集200帧、16个完整设备窗口。不同镜像和板卡未验证；URX2的基址0x43c10000、ID0x32585255、100MHz仅是本案例参数。

## W2 连续输入下启停的相位排错

**适用场景：** UART持续输入时“偶发坏字节/停止位错误”，尤其每次开启采集附近集中出现。

**输入：** 源端波特率/8N1设置、已知发送字节与参考模型、采集开关和解码复位的关系、错误时间位置。

**步骤：**

1. 排查通信设置和源端本身：串口回环不一致时，不以该模块作可靠黄金源；模式灯应在本轮启动锁定后观察。
2. 比较接收开始相对于位/字节的位置，确定错误是否由字节中途复位、重新找起始位引入。
3. 若确实耦合，考虑持续运行字节解码，仅用采集使能门控**完整字节入队**；会话清除不打断正在接收的字符。换波特率的同步策略单独定义。
4. 以发送相位扫描、重复启停、真正非法停止位、复位与不同波特率验证修复。既要消除监测端自造错误，也要保留真实错误检测。
5. 最后用持续实线数据复测，记录原始字节、时间和错误计数；失败相位与旧版本不删除。

**失败条件：** 无可辨识边界的无限码型不能承诺任意冷启动自动同步；源端自回环失败、波特率不符、输入电平未确认时，不先改业务解析掩盖问题。

**输出：** 根因假设、能复现/反驳的输入、前后版本、相位测试结果和真实错误仍能检出的依据。

**来源与效果：** C1波特率误配和C2持续流修复；C2覆盖5档真实波特率仿真、160组相位/320次启停、37轮真实F103共2312帧。上述数字是本项目历史验证，不是本技能工具执行次数。

## W3 原始流回放和分层归因

**适用场景：** 看到缺号、坏校验、曲线断点或告警时，需要判断采集端与被测设备的责任范围。

**输入：** 原始字节、逐字节硬件时间、实际协议/规则配置、解析记录、事件、采集寄存器、固件与软件摘要；如有则提供源端独立日志。

**步骤：**

1. 核对时间索引长度与原始字节数、一致时间基准、非递减时间和原始偏移。未记录硬件时间的文件只能作有限内容比较，不补造逐字节实测时间。
2. 检查采集错误与计数守恒。仅在该硬件契约确认为累计输入/保留/丢弃时，使用“输入=保留+丢弃”；不能对任意同名寄存器套用。
3. 从保存的字节与时间重新解码，比较原始值、换算值、有效性、校验/序号统计。调用项目适配器时，确认它与产生记录的软件版本相容。
4. 从相同时间轴重新执行规则，并与硬件事件批、PS事件和窗口交叉核对。软件回放不重跑FPGA；硬件结果仍须原始批记录证明。
5. 缺少校验或序号则对应检查不具备判断条件；采集丢失时不能要求缺失的逻辑事件与完整源一致。已有明确字段告警继续保留，没有足够业务证据时设备UNKNOWN。

**失败条件：** 摘要/解码不一致、时间重启未分会话、原始范围越界、配置或源端身份不明。数据不足时保留未判定范围，不用0或插值凑齐。

**输出：** 文件完整性、采集、协议、设备和逻辑回放可比性分别判断。

**来源与效果：** C3中独立电脑接收源端200帧正常，而PYNQ本地停读16秒丢834字节，解析172帧；验证结果保留capture FAIL、protocol FAIL、device UNKNOWN。没有把本地错误算作小车故障。

## W4 连续多事件和持久保存重试

**适用场景：** 一次异常恢复后再出现、多规则同时命中、取证窗口重叠、写盘失败需要恢复。

**输入：** 规则持续/恢复语义、事件ID及源帧范围、前后窗长度、等待/总窗口上限、保存台账和失败请求。

**步骤：**

1. 每条规则维护持续条件与锁存。条件恢复后允许再次触发；无效输入或时间基准重启按契约清除连续性。
2. 同一帧保留全部规则命中及共同时间戳，避免优先级只留下一个告警。区分硬件事件批容量、软件待保存容量和磁盘窗口上限。
3. 每事件定位真实可用前窗，继续采集后窗；共享原始数据不妨碍不同事件独立标注。启动不足、提前停止、丢失或容量满均明确报告。
4. 窗口后台保存并回读摘要，原始采集与页面刷新分离。窗口失败时持久保留请求与错误，不宣称原始流也一定失败或一定完整，分别核验。
5. 在已授权的隔离目录恢复明确的路径阻塞后，重试已有请求；不重新采集替代原现场，不改原始字节和告警。阻塞仍在则重试继续失败，避免无界自动重试。

**失败条件：** 满容量、后窗未收完、写盘错误、原始介质失效须保留实际状态。无法证明每条事件有独立窗口时不能宣称全部保存。

**输出：** 事件数量、时间、原因、完整/截短窗口数量、失败/待处理/丢弃数量、每次保存尝试和源摘要。

**来源与效果：** startup2两批各8条规则形成16个完整设备窗口；另有发送前后超时，共18个窗口，不能把18说成18次设备故障。C4实际ENOTDIR阻塞在第三次保存时恢复，200帧源摘要不变。未验证SD损坏、磁盘满或写入中突然断电。

## W5 固定版本和可复核交接

**适用场景：** 发送给队友、制作报告、冻结演示版本，或将技能迁移到另一题目。

**输入：** 选定的源码/固件/配置/验证结果范围、版本身份与未完成清单。

**步骤：**

1. 将构建、实板、历史回放、界面检查、封存核验列为不同结果；明确本次只封存运行文件还是完整工程。
2. 用 `check_snapshot.py create` 建立严格文件集合、大小和SHA256；清单置于源目录外，额外固定其摘要。摘要保护完整性，不提供签名身份认证。
3. 将选择的技能目录复制/解压到新目录，执行自检和清单核验；再用显式提供的工程源码对真实记录运行 `audit_record.py`。
4. 在测试副本修改文件或新增文件，确认工具拒绝。只在副本做负向验证；生产记录不覆盖。
5. 报告按最新收据更新，保留旧资料包的历史状态与失败。新bit/HWH、规则或关键软件变动后评估哪些验收要重做；不让旧实板结果代表新版本。

**失败条件：** 输出混进源清单、依赖个人绝对路径、缺源码/适配器、核验工具与生成版本不相容。干净目录回放不等于从零Vivado构建或陌生队伍实板复现。

**输出：** 固定版本摘要、验证命令及运行环境、成功与失败收据、可复用范围与未测条件。

**来源与效果：** C5运行快照51文件，其中26运行文件与板端一致；旧资料包曾在新解压目录核验1627项、回放58记录。新技能自己的实际验证结果见validation.md，二者不混写。
