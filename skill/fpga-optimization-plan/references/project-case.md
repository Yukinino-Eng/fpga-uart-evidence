# 案例：规则下沉与页面改进分别解决对应问题

这是项目过程的归纳，不是完整提示词/回答原文。下列“判断”描述采用的工程方向，“结果”只引用已有收据和说明，不新增性能测量。

## 用户提出的架构问题

用户先问“FPGA有实现并行计算吗”“现在有多少能集成到FPGA上，体现并行计算能力”，继而要求“进行FPGA集成，按照你的推荐来，先完成离板验证”。同时关心既有可视化是否受影响，以及系统距离高速信息流还有多远。

## 采用的分工

| 位置 | 本项目处理 |
| --- | --- |
| FPGA 输入与协议通路 | UART字节、硬件相对时间、定长分帧与校验、有限整数提取、序号/超时 |
| FPGA 规则 | 八个独立规则实例；各自持续确认、触发及恢复，保留同帧全部命中 |
| PS | 通用文本/浮点/插件解析、软件规则回退、配置与文件管理、保存与展示 |
| 界面 | 消费统一字段、事件和窗口结果，同时说明规则来源、当前能力与保存状态 |

分帧与 CRC 仍按字节处理；八规则并行不等于八路串口或整条链路全并行。同一 URX2 固件可选择通用软件规则，文本接入不要求重新构建 bit。超出硬件配置能力的内容不能静默按另一种含义执行。

## 正确性与实现代价

`docs/uart-monitor/fpga-detector.md` 保留早期离板方案、实现报告入口及历史实板阶段；不能只读该文早期“待测”段落判断当前状态。最新版结果见 `build/uart_latest_binary_acceptance_20261101_01/completion.json`：9600/115200各200帧的八路用例，每轮两批各8条设备事件及16个完整窗口；持续越限触发、短毛刺不触发，独立回放一致。

startup2 的资源与时序来源为 `docs/uart-monitor/startup-sync-fix.md` 及其构建记录：100MHz，WNS=0.000ns，WHS=0.044ns，LUT15971、FF13887。余量处于报告边界，不由此保证长期/PVT稳定。没有同条件 CPU 性能对照，不宣称八倍加速。

配置100ms持续阈值，按到达的有效样本进行确认；10Hz输入可能在后续采样帧才确认，历史用例约200ms。确认阈值不是端到端最大告警延迟。

## 另一个瓶颈的不同处理

实际 Notebook 曾因全量 JSON 快照反复传输而显示滞后，`docs/uart-monitor/notebook-live-check.md` 记录了独立接收与页面路径的区分，及采用完整快照无损压缩传输的修复。

该记录最近2000帧的原 JSON 约2510942字节，传输约192718字符；这是特定记录的观测，不是固定压缩比。浏览器原生解压后逐字段一致，压缩损坏被拒绝；旧组件嵌套显示和错误超时标签也单独修复。

联合采集300.045秒、15028帧的原始文件和回放通过；页面超时标签修正后另做60.050秒、3006帧静态复测。浏览器54个样本没有错误超时标签或延迟提示。页面目标刷新间隔不构成硬实时保证。

## 下一项目怎样套用

先写“假设：哪一段限制了什么结果”，再定义可推翻它的观测。例如：

- 认为规则执行是瓶颈：测相同输入的处理时间/排队与规则数关系，并检查资源和输出一致性。
- 认为页面慢导致丢数据：同时看原始采集计数、排空队列与页面时间；若采集未丢且传输量很大，先试显示路径优化。
- 认为并行规则能让UART更快：分别核对线上有效负载与规则处理能力；二者不是同一限制。
