# PYNQ 固件加载与身份核验

## 用途与适用场景

在 PYNQ 上接管、切换或恢复 PL 设计时，先确认当前运行的是什么、能否切换，再访问寄存器。离板任务仅检查配对文件和契约，不自动连接板卡。

## 输入与前置条件

需要目标 bit、对应 HWH、版本摘要、板卡与镜像信息，以及当前设计的身份/空闲契约。HWH 是运行时硬件描述；XSA 是构建导出物，不能直接当作 HWH 的替代文件。寄存器访问采用项目已验证的驱动；有些设计使用 register_map，有些使用集中定义的 MMIO。

## 执行步骤

1. 核对目标文件摘要、ID、接口版本、能力和地址映射，区分“主机文件匹配”与“板上当前身份匹配”。
2. 取得项目约定的独占访问权。对已经识别的设计确认接收停止、DMA 停稳、FIFO 与待处理事件已交接。未知设计不能靠猜测 MMIO 地址证明空闲。
3. 当前任务要求加载且条件成立时，执行一次明确的下载。先确认 SDK 构造函数是否自动下载，避免构造 Overlay 后又无条件调用 download()。
4. 回读已知身份和空闲状态，再开新会话。普通页面重连若已证明设计匹配，应复用状态，避免隐式重载抹掉现场。
5. 重启后分别检查启动编号、网络/Notebook、实际 PL 设计、历史文件和新采集；系统启动成功不代表业务固件已恢复。

## 失败条件与处理

身份或摘要不符、锁被占用、活动采集、待读数据和未知运行设计均阻止依赖它们的写操作。给出具体阻塞项，保存现场；不绕过保护、不顺带刷系统卡或 QSPI。固件变化后，旧记录仍描述旧版本，不能作为新版本实板通过依据。

## 输出与验收

输出目标摘要、实际身份、操作前后状态、是否发生下载及未完成项。正常路径应能加载后核对身份；活动采集和错误摘要应被拒绝。离板检查只能给出文件/契约结论。

## 来源与已验证效果

旧稿来自 SBB4/SBB5 多固件、多页面共存时的混配风险。URX2 历史正常关机后断电记录进一步验证了人工恢复流程：1228 个原有文件一致，恢复后新采集 200 帧并保存 16 个完整设备事件窗口。依据是工程中的 `build/uart_power_recovery_20261101_01/completion.json`；这是既有实测，不是本轮新上板，也不证明突发断电自动续采。

## 迁移边界与关联资料

身份机制、地址、锁、启动镜像和空闲定义需要替换；引脚与密码不是通用常量。本技能的判断顺序可以迁移，具体 SDK 调用需匹配目标环境。原稿与收据摘要见整包 [source-index.json](../source-index.json)；该索引依赖完整工程保存的来源文件。
