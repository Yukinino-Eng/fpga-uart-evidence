# 02：测试场景与判定

## P0：八个必须实现的场景

默认10Hz，20秒；故障均从6秒附近开始，保证有前5秒和后5秒正常数据。表中的槽号从0开始。每轮从序号0重启，但必须先结束上一轮采集或明确分开会话；跨轮重启被检测出来属于正常结果。

| SW4/SW3/SW2 | 场景 | 精确定义（默认10Hz） | 主判定 |
|---|---|---|---|
| 000 | `normal` | 全部正常，槽0～199 | 200有效帧，CRC/缺号/重复/设备规则均0 |
| 001 | `bad_crc` | 槽60的CRC低字节异或01，其他字节和序号不变 | CRC错误1；坏帧不被接受，恢复后缺失序号1 |
| 010 | `skip` | 槽60起序号=槽号+1，仍按原槽发送 | 实际200帧，缺失序号1；没有故意丢字节或断流 |
| 011 | `duplicate` | 槽60起序号=槽号-1；序号为…58,59,59,60,61… | 重复1、缺号0、重启0；设备时间仍按槽增长 |
| 100 | `gap` | 不发槽60～65，槽66恢复，序号保持槽号 | 194帧，缺失6；250ms有效帧超时1 |
| 101 | `persistent` | 槽60～64令`pitch_mdeg=20000`，其余正常 | 持续100ms确认后`pitch_limit`触发1 |
| 110 | `glitch` | 只在槽60令`pitch_mdeg=20000` | 短于100ms，不触发`pitch_limit` |
| 111 | `parallel8` | 槽60/61及140/141令`fault_code=20`，其余为0 | 两批各8条并行规则事件，共16条；保存16个完整窗口 |

000～110用`ego1_faults.json`；111用`ego1_parallel8.json`。两种配置线协议完全相同，切换PYNQ配置时先停止并排空接收，不重新构建bit。

不要为了“故障看起来更多”额外设置`tx_skipped`、无效标志或多个字段，这会破坏场景隔离。对bad_crc，额外的“缺号1”是坏帧被拒绝后的合理结果；PS可能附带帧间丢弃字节诊断，它与CRC/缺号事件分别保存，不能把总事件数简单固定为1。精确类别和计数以每个fixture的`expected.json`为准。

断流时TX一直为高，没有0x00填充，也不发送错误提示字符串。其最后正常帧起于5.9秒，下帧起于6.6秒；这产生约0.6秒的停发槽和约0.7秒的帧起始间隔。

持续越限从6.0秒开始，10Hz下应在槽61那一帧有效接收后确认；短毛刺在槽61恢复时清除持续状态，不能因为恰好经过100ms而触发。判定使用接收时间，不依赖页面刷新。

111中8条规则的ID为`parallel_0`～`parallel_7`，条件分别为`fault_code > 0`～`> 7`，持续时间0。第一次异常恢复后才会再次触发；连续两帧异常不能重复产生16条。第二次在14秒重新触发，所以总数为16条字段事件，而不是32条。

## 时长、开关和显示

- SW0=0：9600；SW0=1：115200。
- SW1=0：20秒；SW1=1：60秒。故障只在6秒、14秒按表注入一次/两次，长模式后面继续正常发送；不能每20秒循环并把序号归零。
- S0单次按下启动；发送期间再次按下应忽略，先保证整轮可重复和可核对。RST可中止，但这轮记为提前停止，不能作为完整验收。
- 按下前锁存同步后的开关值并做按键去抖；上电和复位不自动发送。结束后保持TX高，等待下一次S0。
- LED建议沿用旧习惯：D1_0 active、D1_1 error、D1_2 completed、D1_3当前速率、D1_4当前长模式、D1_5/6/7分别对应SW2/3/4。具体引脚见参考XDC。
- 不要求额外串口控制、菜单或数码管界面。若保留旧文本程序，用独立文件/构建标识，不要在同一UART流内混入文本。

## 正常负载与P1扩展

优先完成两档10Hz正常60秒及八场景。之后在115200用50Hz正常数据验证2400B/s，至少60秒，目标180秒。50Hz在此处是一个单独构建参数/模式，不占用八场景开关；9600禁止50Hz。本包预置60秒向量，180秒可用工具离线生成。

P1附加三组115200/10Hz/20秒向量，不要求占用新的物理开关，可以用独立构建参数选择：

| 用例 | 修改 | 预期 |
|---|---|---|
| `status` | 6.0～6.4秒`fault_code=1` | `device_fault` 1条 |
| `invalid` | 6.0～6.4秒`flags=0` | `imu_invalid` 1条；倾角值无效，不按0参与范围判断 |
| `restart` | 槽60起序号减60、设备时间减6000ms | 重启/乱序1；随后新序号连续 |

## PYNQ端判定注意

八路事件窗口必须启用`continuous`模式；本包两份配置均指定前5秒、后5秒、等待队列32、最多100窗口。64批硬件事件FIFO是另一个容量，不能当成可保存窗口数。

对照计数时只评价**本轮首帧至计划发送结束**。用户按键前的等待和发送结束后继续接收超过250ms，都会合理产生超时提示，须单独标注为启动/计划停发阶段，不能隐藏，也不能归为本轮注入错误。建议先开始PYNQ采集，再按S0，并在日志中保留首末帧与人工操作时刻。

硬件事件时间为本次PYNQ运行相对时间；fixture时间以EGo1开始发送为零。绝对数值不相等时先对齐首帧，不能要求两板计时原点相同。`timestamps_model.bin`只作参考，真实时间索引必须由PYNQ采集保存。

采集端FIFO溢出、解析过载、存储失败单独报告，不能解释成EGo1设备故障。不要主动提高负载到丢数据再声称被测设备出错；过载测试须单独命名并明确是本地压力验证。
