# 过载与窗口保存失败恢复检查

2026-11-01完成第3项的受控实板边界测试。记录位于`build/uart_failure_acceptance_20261101_01/`；[实测回放](../../deliverables/URX2_过载与保存恢复_实测_20261101.html)可切换过载、首次保存失败、阻塞未解除时的重试失败，以及恢复成功四个阶段。

## 实际FIFO过载

沿用当前EGo1 LAB发送程序和两根连接线，115200、正常200帧模式。接收器首次看到输入后故意停止硬件读取16秒，默认有界接收泵仍启用，没有绕过实际FIFO。

- 硬件观测到FIFO为4096条、RECEIVED为4930、OVERFLOWS为834。
- 最终输入6178字节，保留5344字节，丢失834字节，计数满足`received = consumed + overflows`。
- 解析172帧，CRC错误1、缺号28；相应协议异常由此次采集损失引起，不能直接归因于设备。原始缺失不补造。
- `local:fifo_overflow`记录1次，采集完整性FAIL、协议完整性FAIL、设备状态UNKNOWN。电脑COM8独立接收全部200帧、6178字节，与正常发送向量逐字节一致。
- 电脑复核保留的原始数据、时间、解码统计和窗口摘要一致；因本地输入丢失，完整设备规则一致性标为不具备判断条件，不填写“通过”。

本用例的检查通过，含义是系统如实报告了预期的采集失败；该轮采集本身仍为FAIL。它不是高速满线速吞吐测试。

## 真实文件系统错误与恢复

第二轮使用LAB状态位告警场景，115200、200帧。只在本轮新输出目录创建一个占用`events`路径的普通标记文件，窗口创建因此实际收到Linux `ENOTDIR`（errno 20）；没有mock导出函数，没有填满系统盘或修改挂载设置。原始流的路径保持可写。

1. 首次保存失败后仍继续采集。最终200帧、6178字节，与电脑独立接收逐字节一致；CRC、缺号、停止位错误及各级溢出均为0。
2. 等待用户按S0的超时提示窗口和源端第6秒状态位告警窗口均失败并进入持久待重试状态。设备告警检测1次，原始流与事件均保留；首次失败时帧数为0，后来仍收到状态告警及全部200帧。
3. 采集结束后，先将失败现场完整取回电脑封存。另一个Python进程通过生产接口`retry_saved_session()`重试；阻塞仍在，第二次保存仍失败，报告及两个待处理请求没有被清空。
4. 验证标记内容及路径后，将标记移到保留文件名，解除本轮阻塞；第三次保存成功，两个窗口均读回校验通过。设备告警窗口完整保留前5秒、后5秒；等待输入的窗口仍保留启动前窗裁剪和无数据的真实情况。
5. 原始字节、逐字节时间、解码记录、帧索引、问题与事件日志、协议配置、来源摘要在恢复前后全部一致。只更新保存台账、尝试编号及报告；未重新采集或覆盖旧尝试。

失败时报告为`status=FAILED`、`capture_integrity=PASS`、`protocol_integrity=PASS`、`evidence=SAVE_FAILED`。恢复后为`status=COMPLETED`，两个窗口均已保存、待处理为0；`device_health=FAIL`及原状态位告警保留，因为保存成功不能抹去被测源的告警。该告警是EGo1故意注入的数据，不是对真实小车的故障诊断。

此次覆盖异常窗口目录操作失败、停止采集后的持久重试和恢复；未覆盖SD卡物理损坏、整盘写满、原始流写入介质故障或保存中断电，不将这些情况列为已验收。
